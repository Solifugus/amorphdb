# PWA User Identity and Authentication

## Overview

PWAs built on AmorphDB distinguish between two identity layers:

- **Mesh agents** are AmorphDB's native identities — the node agents that
  operate the mesh and the mobile agents (humans, AI programs, bridge nodes)
  that connect to it. A mesh agent authenticates with post-quantum keys and
  has permissions on the persistent tree.
- **App users** are the end users of an application. They are managed by the
  app, not by AmorphDB. They do not have mesh identities, keys, or permissions
  on the mesh at large.

This separation matters because the two populations have different lifecycles,
different authentication needs, and different trust relationships. A
subscription-based SaaS with 100,000 end users does not want 100,000 mesh
agents with cryptographic keys — it wants an application-defined user model
where authentication, signup, password reset, and account deletion are all
application logic. AmorphDB provides the data shape, the routing, and the
security boundary; the application decides what a user is and how they prove
identity.

The rest of this section specifies the platform contract. The application
author writes watchers against the contract; the platform handles routing,
token lookup, and permission enforcement. **The developer does not write
session logic, identity resolution, or HTTP plumbing** — those are the
platform's job.

## Devices, Users, and Tokens

Every browser connection has a **device identity** before anyone logs in.
Every authenticated user has a **user identity** after login. Tokens bridge
the two.

```
world.apps.<app>
    app                         # shared UI definition (parsed from app.html)
        _token_ttl: 604800      # login timeout in seconds (from app.html)
    assets                      # static files served by the Go layer
    devices                     # pre-auth browser connections
        d8f2a1b3...             # device ID (generated by boilerplate)
            login               # login form data lands here
            signup              # signup form data lands here
    users                       # authenticated user data
        kalevo
            banner
                user_name = "Kalevo"
            workspace
                orders = [...]
        miratu
            ...
    tokens                      # active auth tokens
        a7f3c1b9...             # opaque token string
            identity: "kalevo"
            device: "d8f2a1b3..."
            @ttl: 604800        # seconds, from app._token_ttl
    auth                        # app-defined auth state
        credentials
            kalevo
                password_hash: "..."
                salt: "..."
```

### Device Identity

The device ID is generated by the boilerplate JavaScript on first visit and
stored in localStorage permanently. It identifies the browser/device, not
the person. The same person on two browsers has two device IDs. The same
browser always has the same device ID.

Before login, the Go bridge routes writes to
`world.apps.<app>.devices.<deviceId>.*` — only the `login` and `signup`
sub-paths are writable. All other paths are rejected with 401. This gives
the unauthenticated browser a place to submit credentials without having
access to any user data.

### User Identity

The `users.<identity>` subtree is the permanent home of each user's data.
It persists across connections, devices, and disconnections. The identity
itself is a string chosen by the application — a username, an email, a UUID,
anything the app prefers. AmorphDB does not interpret it.

A user can be logged in on multiple devices simultaneously. Each device has
its own token, and each token maps to the same identity but a different
device. The Go bridge uses the device ID to determine which SSE connection
to push updates to.

### Tokens

The `tokens.<token>` subtree holds short-lived credentials that map a
device to a user identity. Tokens are opaque strings generated by the
application at login time. Each token carries:

- `.identity` — the user identity string (e.g., `"kalevo"`)
- `.device` — the device ID of the browser that logged in
- `@ttl` — time-to-live in seconds, set from `app._token_ttl`

Tokens expire automatically via AmorphDB's purge mechanism. No cleanup
watchers are needed.

### Token TTL Configuration

The login timeout is set in `app.html` as a system attribute on the root
section, in seconds:

```html
<section name="app" token_ttl="604800">
    <!-- 604800 seconds = 7 days -->
    ...
</section>
```

A value of `0` means no timeout — the token persists until explicit logout
or manual removal. The boilerplate parses this attribute and stores it at
`world.apps.<app>.app._token_ttl`. The login watcher reads it when creating
tokens.

## How the Go Bridge Routes Traffic

The Go bridge handles all identity resolution. No MBL interpreter changes
are needed.

### Pre-authentication (device only)

1. The browser generates a device ID on first visit (stored in localStorage).
2. Every MCP request includes the device ID via the `X-AmorphDB-Device`
   header.
3. The Go bridge routes writes to `world.apps.<app>.devices.<deviceId>.*`,
   restricted to `login` and `signup` sub-paths only.
4. SSE events for the device path are pushed to that browser connection.

### Authentication

1. The browser submits login credentials. The boilerplate sends a data
   change to `devices.<deviceId>.login`.
2. A login watcher validates credentials and creates a token (see
   Authentication Flow below).
3. The Go bridge detects the token in the login response and returns it
   to the browser.
4. The boilerplate stores the token in localStorage alongside the device ID.

### Post-authentication (device + token)

1. Every MCP request includes both `X-AmorphDB-Device` and
   `X-AmorphDB-Token` headers.
2. The Go bridge looks up `world.apps.<app>.tokens.<token>`, reads
   `.identity`, and verifies `.device` matches the presenting device.
3. All writes from that request are routed to
   `world.apps.<app>.users.<identity>.*`.
4. SSE events for that user's data are pushed to the browser connection
   associated with the device.

A request with an expired, unknown, or device-mismatched token is rejected
with 401. The boilerplate detects 401 and shows the login screen.

## Authentication Flow

### Login

```mbl
# Login watcher — processes unauthenticated login attempts
watch my.app.auth.login_handler(world.apps.myapp.devices):
    for device in world.apps.myapp.devices:
        if device.login.submitted = true:
            username = device.login.username
            password = device.login.password

            # Look up credentials (app-defined)
            creds = world.apps.myapp.auth.credentials[username]
            if is_unknown(creds):
                device.login.result = { status: "error",
                                        message: "Unknown user" }
            else:
                if verify_password(password, creds.password_hash, creds.salt):
                    # Generate token
                    token = generate_token()
                    ttl = world.apps.myapp.app._token_ttl

                    # Write to platform token slot
                    world.apps.myapp.tokens[token].identity = username
                    world.apps.myapp.tokens[token].device = device
                    if ttl > 0:
                        world.apps.myapp.tokens[token].@ttl = ttl

                    device.login.result = { status: "ok", token: token }
                else:
                    device.login.result = { status: "error",
                                            message: "Invalid password" }

            # Clean up
            device.login.submitted = (quietly) false
```

### Signup

```mbl
# Signup watcher — creates new user accounts
watch my.app.auth.signup_handler(world.apps.myapp.devices):
    for device in world.apps.myapp.devices:
        if device.signup.submitted = true:
            username = device.signup.username
            password = device.signup.password

            # Check if user exists
            existing = world.apps.myapp.auth.credentials[username]
            if not is_unknown(existing):
                device.signup.result = { status: "error",
                                         message: "User already exists" }
            else:
                # Create credentials
                salt = generate_salt()
                hash = hash_password(password, salt)
                world.apps.myapp.auth.credentials[username].password_hash = hash
                world.apps.myapp.auth.credentials[username].salt = salt

                # Create user data subtree (mirrors app structure)
                world.apps.myapp.users[username]._shown = true

                # Set up per-user watchers
                my.app.setup_user_watchers(username)

                # Auto-login
                token = generate_token()
                ttl = world.apps.myapp.app._token_ttl
                world.apps.myapp.tokens[token].identity = username
                world.apps.myapp.tokens[token].device = device
                if ttl > 0:
                    world.apps.myapp.tokens[token].@ttl = ttl

                device.signup.result = { status: "ok", token: token }

            device.signup.submitted = (quietly) false
```

### Per-User Watcher Registration

Every user gets their own watchers, registered at signup time. One watcher
per user, not one watcher for all users. This is the only pattern — there
is no "watch all users" alternative.

```mbl
my.app.setup_user_watchers: procedure(username):
    user_path = world.apps.myapp.users[username]

    # Order submission
    watch my.app.watchers[username & ".submit_order"](user_path.intent.submit_order):
        if user_path.intent.submit_order = true:
            world.apps.myapp.shared.orders..append({
                user_identity: username,
                items: user_path.forms.order_data.items,
                submitted: now()
            })
            user_path.intent.submit_order = (quietly) false
            user_path.intent.result = { status: "submitted" }

    # Logout
    watch my.app.watchers[username & ".logout"](user_path.intent.logout):
        if user_path.intent.logout = true:
            # Remove all tokens for this user
            for token in world.apps.myapp.tokens:
                if token.identity = username:
                    world.apps.myapp.tokens..remove(token)
            user_path.intent.logout = (quietly) false
```

This approach:
- Fires only when that specific user's data changes (no looping)
- Scales linearly — 1000 users means 1000 watchers, each lightweight
- Is explicit — you can see exactly what watchers exist for each user
- Cleans up naturally — delete the user's watchers when deleting the account

## App User Scenarios

The platform contract supports all common user models without modification:

### Guest users only (no login required)

The app never requires authentication. All data lives under
`devices.<deviceId>`. No tokens, no users subtree. The Go bridge routes
everything to the device path. The device ID in localStorage provides
continuity across visits.

### Registered users only

The app requires login. The Go bridge rejects all non-login/signup traffic
from unauthenticated devices. The `app.html` does not include a signup
section. An admin or batch process populates `users` and `auth.credentials`.

### Self-registration

The app allows signup. The `app.html` includes a signup section visible
before login. The signup watcher creates the user, credentials, and
per-user watchers.

### External registration

Users are created by an external system (HR import, admin panel, API).
The external system writes directly to `users` and `auth.credentials`
via MBL or the inbound request queue. The PWA only shows a login form.

### Third-party authentication (OAuth, SSO)

The login watcher redirects to the provider (via an outbound HTTP call or
by writing a redirect URL to the device's login result). The provider's
callback arrives via the inbound request queue. The callback watcher
validates the provider's token, creates the AmorphDB token, and associates
it with the device that initiated the flow.

```mbl
# OAuth login — step 1: redirect
watch my.app.auth.oauth_login(world.apps.myapp.devices):
    for device in world.apps.myapp.devices:
        if device.login.provider = "google":
            # Store device ID for callback matching
            state = generate_token()
            world.apps.myapp.auth.oauth_pending[state].device = device
            device.login.result = {
                status: "redirect",
                url: "https://accounts.google.com/o/oauth2/auth?state=" & state & "&..."
            }
            device.login.submitted = (quietly) false

# OAuth callback — step 2: validate and create token
watch my.app.auth.oauth_callback(
    world.apps.myapp.requests[path ?= "/auth/callback"]
):
    for req in world.apps.myapp.requests[path ?= "/auth/callback"]:
        state = req.query.state
        code = req.query.code
        pending = world.apps.myapp.auth.oauth_pending[state]

        # Exchange code for provider token
        provider_result = my.computer.network.web.post(
            "https://oauth2.googleapis.com/token",
            "code=" & code & "&..."
        )

        # Extract user info, create or find user
        user_info = my.computer.network.web.parse_json(provider_result.body)
        username = user_info.email

        # Create token
        token = generate_token()
        world.apps.myapp.tokens[token].identity = username
        world.apps.myapp.tokens[token].device = pending.device
        world.apps.myapp.tokens[token].@ttl = world.apps.myapp.app._token_ttl

        # Clean up and redirect
        world.apps.myapp.auth.oauth_pending..remove(state)
        my.computer.network.web.redirect(req, "/?token=" & token)
```

## Security Boundary

The PWA security model has three enforcement layers:

1. **Mesh permissions (AmorphDB-native).** The daemon runs as a mesh agent.
   That agent must have `@write` on `world.apps.<app>.*` for the Go bridge
   to operate. This is set up once at app deployment time.

2. **Go bridge enforcement (platform-native).** The Go bridge enforces:
   - Unauthenticated devices can only write to `devices.<deviceId>.login`
     and `devices.<deviceId>.signup`
   - Authenticated users can only write to `users.<their_identity>.*`
   - No browser can write to `app`, `assets`, `auth`, or `tokens` directly
   - Token-to-device matching prevents token theft across devices

3. **Watcher-level validation (application-native).** The app's watchers
   mediate between user data and shared data. A user writing to their
   `intent.submit_order` does not directly modify shared order records — a
   watcher reads the intent, validates it, and only then writes to shared
   data. This is the standard mediation pattern for cross-boundary data flow.

## Reference Authentication Scheme

Authentication itself is app-defined. However, because nearly every app
needs password authentication and nearly every app gets it wrong, the
AmorphDB PWA boilerplate ships with a reference implementation:

- Password hashing via Argon2id with per-user salt
- Token generation from the platform's CSPRNG
- Standard login, signup, password change, and logout watchers
- Brute-force protection via a rate-limit counter on recent failed attempts

Apps that want OAuth, SAML, SSO, passwordless magic links, or hardware keys
replace the login watcher. The token handoff and the security boundary are
unchanged — only the credential validation logic changes.

See `AmorphDB_PWA_Boilerplate_Spec.md` for the reference implementation.

## What the Developer Writes

With the reference auth scheme in place (provided by the boilerplate), a
minimal PWA backend for a multi-user order form requires only the
application-specific watchers:

```mbl
# The boilerplate provides:
#   - login_handler watcher
#   - signup_handler watcher
#   - setup_user_watchers procedure (called at signup)
#
# The developer adds application logic to setup_user_watchers:

my.app.setup_user_watchers: procedure(username):
    user_path = world.apps.myapp.users[username]

    watch my.app.watchers[username & ".submit_order"](user_path.intent.submit_order):
        if user_path.intent.submit_order = true:
            world.apps.myapp.shared.orders..append({
                user_identity: username,
                items: user_path.forms.order_data.items,
                submitted: now()
            })
            user_path.intent.submit_order = (quietly) false
            user_path.intent.result = { status: "submitted" }
```

No HTTP handlers. No session management. No authentication code. No SSE
plumbing. No identity resolution. No new MBL keywords. The developer writes
one procedure that sets up per-user watchers, and the platform handles
everything else.
